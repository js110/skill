# 动态档案、称重和参考复核

## 记录原则

资料是有日期的记录。不要用首次录入值永久计算，也不要把最新资料倒灌到过去。每次操作读取本地状态，再处理用户新信息；实际变化与假设、测试、他人信息分开。无需用户学习命令，可接受“今天 148 斤”“从今天开始站着上班”“现在生病需要特殊饮食”等自然表达，或清晰的体重秤照片。

- `profile_versions`：资料的完整版本、生效日、记录日和变更原因。年龄、身高、公式系数、活动量、目标及健康信息都可更新。没有生日时不编造生日或精确增长后的年龄，按复核时的实际年龄更新。
- `weights`：原始体重值、日期和来源，单位统一 kg；市斤转 kg 用除以 2。同一天多次读数保留，趋势计算每天用最后一条有效记录，避免一天称多次被加权。更正以新记录替代旧记录，旧值保留撤销标记。
- `days`：食物数据和当时参考的快照。当日资料变更可刷新当日参考，旧参考留在 `target_history`；此前日期的预算不自动改写。补记旧餐使用该日已冻结参考，若该日没有快照则使用该日有效的资料，不能用未来体重算过去。

## 体重趋势和热量参考

最近七天至少有三天有效称重时，用这几天的平均值作为需求估算中的体重依据；不足时使用最近一次体重并注明记录日期。只展示有数据的点，不插值填满空白日期。前七天也至少有三天时可比较两段均值；这是记录趋势，不能从体重波动判断脂肪变化或精确反推热量。

用户选定的摄入参考（例如约 2000 kcal）与重新估算的维持需求是两个字段。前者不会自动跟着每次体重变化上下摆动。相对上次确认计划时的基准体重，新的体重依据变化达到 2% 时，标记计划待复核；它是产品复核阈值，不是医学界限或准确率。新需求仍可查看，旧摄入限额先不作为“超额”判断依据。用户选定合适的新目标后用 `confirm-plan` 启用。

活动量、目标、健康/用药等关键情况发生变化时立即标记计划待复核。不能从“站着工作”直接推断为高强度活动；必要时用一个短选项了解日常活动。健康事件需要更新 `special_care` 与简短说明；信息不足时保留待复核状态，不据疾病名称自行开饮食处方。体重更新不能清除健康暂停，用户说恢复后仍需确认当前计划再启用。

## 接口

沿用 `daily_log.py --state STATE.json --request REQUEST.json --output SUMMARY.json`，各操作的 `date` 是处理这次消息的用户当地日期；可选 `effective_date` 是实际生效日。食物操作的 `date` 仍是实际食用日。

```json
{"operation":"weight","date":"2026-10-22","id":"weight-2026-10-22-1","value":148,"unit":"jin","source":"user_report"}
```

`weight` 需要稳定 ID，防同一条消息/照片重复。`unit` 为 `kg` 或 `jin`，`source` 为 `user_report` 或 `scale_image`。补记称重加 `effective_date`；更正加 `replace_id`，保留旧数据撤销标记。`remove-weight` 传 `id` 可撤销。实际读不到秤上数值时不猜数值。

```json
{"operation":"update-profile","date":"2026-10-22","changes":{"activity":"active"},"reason":"用户报告日常活动变化"}
```

`changes` 只放本次实际变化；其它字段沿用对应日期的版本。支持 age、height_cm、sex_coefficient、activity、goal、goal_weight_kg、special_care、health_note、medication_note、allergies、preferences。体重必须用 `weight`，保留测量历史。未来生效的资料在日期到来前不作用于当前参考。

```json
{"operation":"update-profile","date":"2026-10-22","changes":{"special_care":true,"health_note":"用户报告需要特殊饮食照护"}}
```

此时继续记录食物，暂停限额、余额与超额判断；不输出低热量补偿建议。健康情况改善不能通过单独称重或更改活动量自动取消暂停。

- `review-profile`：`date`, `confirmed:true`。仅当用户确认未改字段仍适用时刷新整体资料复核日；单独称重不算重新确认健康情况。
- `confirm-plan`：`date`, `confirmed:true`, `target_override`（明确的 kcal/low/high/basis，或 null 表示仅启用维持参考）。仅在用户选定当前计划、资料有效且不处于特殊照护时执行；不能自动调用来消除提示。
- `review-noted`：`date`, `keys:["weight","profile","plan"]` 的实际已提示项。只记录提示已送达，不代表用户回答“没变化”。
- `migrate`：`date`。将旧版状态升级，保留原餐次、参考和当前资料；无法从旧文件恢复的早期资料不伪造。普通写入也会自动升级；只读 summary 不改文件。

旧 `set-profile` 保留兼容，需提供完整档案，适用于首次补齐或明确全量替换；日常变化优先用 `update-profile`。`retarget` 是用户明确要求重算某一天，不应拿它批量覆写过去。

## 复核频率

每次用户使用时检查 `summary.review`：

- 一周无新体重：有机会时提示一次“方便时记个体重即可”；不阻止发图记餐。
- 三十天未确认整体资料：简短确认近期活动量、健康和目标是否变化。
- 同类提示默认七天冷却。发出后写 `review-noted`；被跳过不能当作用户确认。涉及健康变化时，正常提示冷却不解除健康暂停。
- 九十天未复核：个人热量限额暂不可用，只累计食物。用户重新确认资料后才恢复适用参考；有计划变更原因时还需重新确认计划。

这些频率是避免信息长期失效和过度打扰的默认流程。不是后台监控：Skill 不会自动发现用户换工作、生病或体重改变，只能使用用户报告、秤图或复核回复；也不会在聊天关闭后自行定时提醒。

摘要增加 `weight_trend`、`review`、`review_note`、`maintenance_reference`，并保留 `target_snapshot` 供历史对照。已保存的旧快照不能绕过健康暂停或资料过期：这些情况下当前有效 `target` 为 null，不再比较吃超；旧快照仅作留档。资料值和健康说明保留本地；默认食物分享卡只显示资料复核日期与必要提示，不展示完整体重史或健康说明。体重图/报告仅在用户需要查看趋势时生成，清楚标注未记录的日期。
