# 只发图的中国餐食估算

## 交互约定

完成首次档案后，用户每次只发食物图即可。助手自行查看、识别、查资料、估量、记账、出卡，不例行追问菜名、克数、肉种、做法、用油或吃了几成；小建议也不要变成“告诉我是什么”。个人餐盘默认图中可见可食部分为本次食用份量，记录标为暂估；无法由图片证明吃完。照片有明显共享大盘、多人餐具时，先按可见食物中的一人常见份量情景暂计，并显著说明“共享餐食，按一人份暂估”，而不是把整桌都扣到个人账。无法从图像支持合理的一人份时只展示整桌范围，个人日志暂不增加，不编造人数。用户自愿纠正可直接更新；不是正常流程的前置要求。

新照片看起来是同餐补拍，优先合并或修正原条目而不是新添一次；同条消息多视角不重计。吃前/吃后图有可比容器时估计差额；只见被咬后的食物只计可见剩余，不猜已吃多少。截图可先读包装营养表、餐厅规格、秤读数等；识别标签不是另找用户打字。不清晰或明显不是食物时不生成虚构数字，只说明本图无法形成可靠估算；不以连串问题收尾。

## 内部视觉分析（默认折叠到依据）

1. 划分食物区域，记录可见证据：主食形态、肉脂肪、蔬菜、酱汁、面饼层次、容器、遮挡和画面截断。没有实物尺寸参照时，餐盘直径、手大小、勺碗尺度只能作为常见尺寸的推测，不能称作测量。
2. 先确认大类和做法，再给一个对卡片有用的名字。无法分辨羊/猪时使用“烤肉串”，白色条状物无法区分豆皮/面食时保持中性名称，不强行命名。含糊但影响热量的部分保留 2–3 个相容候选，内部比较，不要求用户选。
3. 对常见中餐按组成估算：主食、肉蛋豆、蔬菜、油糖酱汁。没有精确菜名也能计算。单独拆油只用于参照项未含该油的情况；成品菜谱数据、炸物数据、肉自身脂肪不能重复加。
4. 份量给中心和上下界；热量密度给最匹配参照和必要的替代情景。肉的肥瘦、粉皮含水、烧饼起酥用油、汤中乳化脂肪由候选情景表示。不要把图片亮度、颜色、油光或奶白汤色当作测油或含奶的证据。
5. 输出一张卡即可：有用的菜名、约多少大卡、情景范围、默认食用口径、影响最大的 1–2 项不确定因素、当天累计和一个实际饮食建议。详细计算/来源放折叠区；不输出候选菜谱的大段推理，不附一串追问。

## 数据查找与来源

优先级：图中可读且匹配规格的包装/餐厅营养资料 → 可访问的中国食物成分表对应条目 → 香港食物安全中心（CFS）对应食物或配料 → 其他可信成分数据库 → 明确标记的经验情景。

- [中国营养与健康所平台说明](https://www.chinanutri.cn/yyzyxxpt/sjzx/swcfsjk/201911/t20191128_207183.html) 说明其平台数据主要来自《中国食物成分表》。[公众平台](https://fq.chinafcd.org/) 可访问性会变化，不能把说明页或未成功查询的站点当作数值来源。本次制作时该站连接失败，未导入其完整数据。
- [CFS 营养资料](https://www.cfs.gov.hk/sc_chi/nutrient/) 有中式成品与配料及来源说明，适合匹配中餐；条目本身仍不代表眼前这家店的配方。[使用者指南](https://www.cfs.gov.hk/sc_chi/nutrient/searchmenu.php) 提醒食物营养会随来源和处理方式变化，数据仅供个人非商业参考。依此使用，避免批量复制数据库或宣称商用授权。
- `nutrient-catalog.json` 是少量实际查过的参考条目和取得日期、代码、原始响应摘要哈希，支持离线启动，不是完整中国菜库。条目中的英文生熟/含脂肪等说明必须匹配，不能把瘦烤羊肉当作肥五花肉。

未命中本地条目时，使用 `scripts/cfs_lookup.py` **在线查询**，不把查菜名的工作交给用户。工具只发送食物查询词与代码，不上传照片或个人资料：

```text
python /skill/scripts/cfs_lookup.py --output /chat/work/matches.json search "rice flour roll"
python /skill/scripts/cfs_lookup.py --output /chat/work/food-record.json get --group 40 --subgroup 02 --food-id 10400200012
```

`search` 结果只是候选名，不是营养证据；`get` 成功返回具体食物、能量和每100g可食部分单位后才算取得数值。工具使用公开查询表单的 POST，GET 同地址可能返回空数据；空白、NA、单位不符、网络失败均不能猜一个数字补上。失败后改用已核对的近似参照或经验情景并披露，不反复查询拖延出卡。在线得到的对象可加入**当前聊天的**临时 catalog 的 `records` 数组，不能自动污染共享 skill 目录。

检索用词可由中文菜拆成配料和英文做法，例如：肠粉 `steamed rice flour roll`，麻婆豆腐 `bean curd minced pork chilli`，饺子 `dumpling`，炒饭 `fried rice`，瘦烤羊肉 `lamb lean grilled`。查到近似值标 `proxy`，不是 `exact`；没有核对来源的手填值标 `experience`。分类表示**数据与食物的匹配**，不是准确率等级或校准概率。

## 确定性计算

用 `scripts/estimate_meal.py` 将观察 JSON 转成卡片/日志 JSON。助手负责图像理解；该脚本不会看图，也不是另外训练的食品识别模型。它负责查本地/临时 catalog、密度×份量、候选范围包络和来源追踪，减少直接编一个整餐数字。

```json
{
  "title":"肉馅肠粉", "meal_label":"拍照即记",
  "portion_basis":"按可见整盘暂估计入，实际食用量未确认",
  "confidence":"粉皮厚度与用油为推测",
  "visual_evidence":["可见蒸粉皮、肉馅和叶菜，盘内有淋汁"],
  "uncertain":["粉皮含水量与厚度", "淋汁和用油摄入量"],
  "components":[
    {"name":"粉皮", "state":"cooked",
     "portion":{"g":250,"low_g":180,"high_g":320,"basis":"依盘中覆盖面积与折叠层数目测，无实测尺度"},
     "density":{"reference_id":"cfs-10400200012","match":"proxy","reason":"以蒸肠粉成品作为粉皮密度近似；本店含水量未知"},
     "alternatives":[{"kcal_per_100g":140,"match":"experience","reason":"较厚、含水少的粉皮情景，非已验证条目"}]}
  ],
  "comment":"软糯和鲜香，都在这一盘。",
  "tip":"下一餐可以搭配一份鱼或豆腐和蔬菜。",
  "assumptions":["此段是格式示例，实际任务需补齐全部可见食物、油与淋汁"],
  "is_demo":true
}
```

`density` 是中心情景；`alternatives` 是合理替代密度，用于范围而非概率平均。各组件中心 `g×密度/100`，范围为 `[low_g×最低候选密度/100, high_g×最高候选密度/100]`，再求和。上下界是保守情景组合，不保证真实值一定落入，不得标“95%准确”或统一±百分比。

```text
python /skill/scripts/estimate_meal.py /chat/work/observation.json --output /chat/work/meal.json
```

在线扩充了临时 catalog 时加 `--catalog /chat/work/catalog.json`。生成的 `assessment` 给卡片显示数据依据类型；每项 `evidence` 保存来源匹配与份量性质。新增食物沿用此结构进入 `daily_log.py`，不把测试图片自动记入用户当天。

图中清晰标签可直接创建当前聊天的临时条目：`{"id":"photo-label-1","food_name":"图中该产品","basis_unit":"ml","kcal_per_100ml":50,"source":{"kind":"image_label","image_reference":"当前第1张包装背面照片"}}`。数值必须实际读到并换算，不能照抄此示例。对液体用 `portion.unit: "ml"` 和 `ml/low_ml/high_ml`，手填经验密度也用 `kcal_per_100ml`；其余默认 `g/low_g/high_g`。程序拒绝把 per100g 直接乘 ml；有明确密度转换时先转换并记录依据。标签配料、净含量与实际吃的量仍须区分，照片看不到的标签不能假装读出。

## 验证与宣传边界

计算测试只能验证数值、来源引用及记账规则。准确性需要另用未参与规则编写的中餐样本：称量原料、油和实际食用量，计算配方参考值（如需测真实食品能量则另做实验测定），按品类统计绝对误差、相对误差和范围覆盖率。自建配方参考也有误差。没有这种独立数据，不能承诺任何准确率；这次三张照片仅作为图像观察、取数和出卡的功能回归样例。
