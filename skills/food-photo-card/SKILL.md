# 食光小卡

把随手拍变成个人的每日餐食手账。默认中文、响应式 HTML，展示本餐热量、当天已记录摄入、每日参考和剩余参照，再给一句趣味点评和具体饮食建议。**首次建档后，默认只发图即可完成整次流程**，不要求用户解释菜名、克数、做法或回答确认问题；用有依据的情景范围处理图片无法确定的部分。执行图像分析前读取 [references/image-first.md](references/image-first.md)，按其中的中餐拆解与来源规则完成估算。

## 首次使用与资料复用

仅从当前聊天已明确关联的路径或用户指定路径读取本地记录；不要搜索并套用其他聊天的个人档案。已有资料只补缺项，不每餐重问。首次使用先发一条简洁的资料收集消息：

> 先给食光小卡建个基础档案吧：年龄、身高（cm）、体重（kg）、用于热量公式的性别（男／女／不便提供，可算范围）、日常活动量（久坐／轻活动／经常活动／体力活动多），以及目标（维持／减脂／增重）。是否有孕哺期、需要特殊饮食的疾病或正在接受进食障碍相关照护？还可以告诉我忌口、过敏和饮食偏好。默认按当前所在时区记账；资料和饮食记录保存在本地，分享卡片不展示身高体重等隐私。

不从照片或用户名推断个人资料。可跳过不愿提供的字段；信息不足时照常估算食物并记账，暂不显示个性热量额度，不编造默认档案。已有专业人员制定的每日目标时，优先询问其适用范围。仅在用户要求重算或资料更新时调整参考，注明生效日期。

## 动态资料与体重

每次续记先读取状态，不依赖聊天记忆中的旧数字。用户实际报告新体重、活动量、目标、疾病或用药变化时，按 [references/profile-updates.md](references/profile-updates.md) 的日期与版本规则更新；“假如一周后”“比如生病了”等举例不是本人现状，不能据此改档。

体重数字或清晰的体重秤照片进入体重时间线，不当成食物。食物图不能推测人的体重或健康变化。每个称重值保留日期、单位、来源；份量修正和称重更正都是可选操作，不要求用户每餐补文字。新信息从生效日起用于需求估算；已记录过去的摄入和预算快照保留，重算当天参考也保存旧版以便追溯。

普通体重变化更新需求依据；用户已经选定的摄入参考与估算需求分别保存，不随一次称重波动机械增减。活动量、目标或健康变化，以及达到计划复核条件时，暂停沿用旧限额，给出复核提示。生病或相关用药信息不明确时只问影响适用性的一个问题，先继续记食物；不能按旧减脂额度判断“吃超”。恢复后确认当前情况和计划再启用。

每次使用检查日汇总中的 `review`。默认一周无新体重、一个月未确认资料时，适时发一次简短复核提示，提示后调用 `review-noted`，至少七天内不重复；未回复仍正常记食物。九十天未复核时暂停个人限额，保留饮食记录。以上天数及体重变化阈值是交互约定，不是医学标准。不创建后台定时任务；关闭聊天后不会主动提醒或获知变化。用户明确要定时提醒时再使用环境支持的提醒能力。

读取 [references/daily-tracking.md](references/daily-tracking.md)，用 `scripts/daily_log.py` 计算成人维持体重的能量参考并维护日志。先清楚告知“估算每日总能量需求（含活动）”，静息代谢不是每日饮食上限。减脂或增重目标先展示维持参考；使用用户提供的适用计划或引导其结合成人专业规划工具确定目标，不自动扣减固定卡路里、承诺体重变化或生成极低热量计划。未成年人、孕哺期及需要特殊照护者采用饮食记录模式，不自动设置限额与超额判断，可采用其专业照护团队已提供的适用建议。

## 每张照片后的记录

先按下节分析照片。用户在记录模式中发个人餐食图，默认按可见整份**暂估计入**，用一行说明口径后直接出卡，不追问是否吃完；明显共享餐食按 image-first 中的分配规则处理。用户自愿说明吃完、半份、分食等则按实际量计入。明确在询问“准备吃什么／菜单／旧照片／示例／别人的餐食”时只做分析，不计入。单纯使用本 skill 不应把本次聊天之前的照片或旧测试自动记入当天。

用稳定餐次 ID 和原图哈希防重。补拍、同餐多视角、同图重发先关联原记录；用户明确同样食物又吃了一份才能新建。份量修正替换原条目，撤销则移除该条目的摄入贡献；补记昨天归入昨天。跨天新建空白日，保留档案和历史，未用额度不滚入次日，运动不自动抵扣食物热量。首次写入时创建随机唯一目录，如 `work/food-photo-card-data/<uuid>/state.json`，把实际路径告知用户并留在聊天中。个人状态不能写入共享 skill 目录；跨聊天只有能定位并读取同一文件时才声称记得。无法持久存储时明确仅本聊天上下文可续记。

每次写入后重新汇总：本次增量、当天已记录中心值及范围、每日参考及范围、相减后的剩余参照。以用户时区和实际食用日期为准，不使用宿主默认日期。记录默认“不完整”，只有用户确认当日食物饮料均已记全才标记完整；漏记的奶茶、零食、酱料不能推定为零。

比较范围后说明“已记录摄入高于参考范围”“低于参考范围”或“范围重叠，是否超出尚不确定”；中心值超过时可说“按中心估算超过约 X 大卡”，同时保留不确定性。未记全时不能说全天达标或尚未吃超。剩余参照为负仍显示差额，不清零掩盖结果；它不是必须吃满的任务，也不是必须停食的命令。

## 看图和估算

1. 先实际查看用户图片，再识别可见食物、烹饪方式、容器和份量线索。把看见的事实和推测区分开。没有照片时请用户上传；示例只能显著标记为演示，不能冒充照片分析。
2. 以用户自愿提供的实际食用量为准。未说明时按可见份量情景估算，卡片写明默认口径。共享餐盘、吃前吃后图和多视角同菜避免重复；不清楚的肉种、白色配料等使用中性名称，自动比较合理候选，不把辨认工作转给用户。图像完全不足时坦诚无法估算，不编造热量。
3. 每项按“可食重量 g × 对应状态的 kcal/100g ÷ 100”估算。生熟、带骨/去骨、沥干/含汤必须匹配；油、酱汁、糖、饮料单独计入或明确已包含在成品数据中，避免重复。被遮挡部分和看不见的油量是推测，不是识别结果。
4. 营养依据优先读取图中包装标签或对应餐厅规格，其次查可访问的中国食物成分数据、香港 CFS 及其他可信数据库。使用 image-first 中的在线查询和少量已核对参照，以具体食物、状态、单位和代码追溯；近似配料标记为近似参照，未查证部分明确是经验情景，不用来源链接为整餐背书。包装上只有 kJ 时用 kcal = kJ / 4.184 换算，并核对每份与每 100g。
5. 给每项一个中心值和合理上下界，结合可见尺度、烹饪方式、含油量构造情景范围；不要套统一误差百分比，也不要把它称作统计置信区间。各项及上下界求和，最终卡片取整到约 10 kcal。说明最影响结果的 1–2 个假设。使用“大卡 / kcal”，避免把 kcal 当作小卡 cal。

## 点评和建议

先描述这一餐可见的搭配，再给一句轻松的话和一个具体、低负担的饮食建议。例如“蔬菜也来赴约了，这一碗挺热闹。”或“这份甜点，快乐也有出场份额。”小建议围绕食物搭配，不以要求用户说明菜名、份量或汤名收尾。

结合当天**已记录**食物、用户偏好和过敏原，提出下一餐 1–2 个具体搭配，例如“番茄豆腐配米饭”“鱼肉、青菜和杂粮饭”。按用户饥饿感与下一餐时间给份量弹性；信息不足时说“已记录的餐食里蔬菜较少”，不能诊断营养缺乏。当天参考剩余较多时推荐正常完整的一餐；中心值接近或超过参考时也保持正常进餐，提供饱腹、搭配均衡的选择，不要求跳餐、挨饿或运动补偿。热量低本身不值得表扬。趣味文案围绕食物和体验，数字反馈温和、中性。

## 生成卡片

读取 [references/card-data.md](references/card-data.md) 的格式，优先用 `scripts/estimate_meal.py` 将视觉组成与来源参照转换为本餐 JSON，再按日志规则记账。调用 `scripts/render_card.py INPUT.json --output OUTPUT.html`；有本地原图时加 `--photo ABSOLUTE_IMAGE_PATH`，有日汇总时加 `--daily-json SUMMARY.json`。修正份量后通过日志脚本导出校正后的餐食 JSON 来渲染。计算、日志与排版用 Python 标准库离线运行；CFS 在线取数需联网，只发送食物查询词或代码，不上传原图或个人档案。图像分析由当前支持图片的助手完成，这不是额外训练的视觉模型。

默认沿用 [assets/card.html](assets/card.html) 的清新绿与柠檬黄、餐盘插画和手账感。有原图时插画自动替换为原照片。可按用户要求调整样式；保持主估算值、范围、食用量口径、误差原因和数据依据可读。宏量营养素仅在用户需要且数据足够时另行扩展，不能凭照片伪造精确克数。

按当前环境的交付目录生成文件，保留 JSON 便于改份量后重新计算；HTML 可离线打开，也可用浏览器打印为 PDF。输出前核对项目不重计、上下界包含中心值、总计对应分项、示例标签正确；有浏览器时检查手机宽度布局。返回卡片链接和一句估算摘要。若当前环境无法生成文件，直接在聊天中给出同样内容的小卡片式摘要，并说明文件能力限制。
